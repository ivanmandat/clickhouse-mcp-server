Спек дашборда

Декларативный JSON, который пишет агент и хранит Postgres. Он же — единственное, что читают адаптер рендера и валидатор схемы. Портируемое подмножество вместо родной модели любого BI-инструмента.

↖ Часть архитектуры: Живая схема

Статус: формат реализован и работает. Спеки хранятся в sem.dashboards с версионированием, валидатор проверяет каждый виджет по контракту ниже, адаптер компилирует спек в дашборд Grafana. Отклонения от описанного здесь отмечены отдельно.

Четыре решения, на которых держится формат

1. Два вида запроса, явно различённых. kind: "metric" ссылается на определение из sem_metrics, kind: "sql" несёт сырой SQL. Это не стилистический выбор: виджеты на метриках переживают переименование колонки без участия агента — правится одно определение, и все виджеты следуют за ним. Виджеты на сыром SQL приходится чинить поштучно.

2. Строки с долями ширины вместо координатной сетки. Grafana использует 24 колонки, Superset — 12, у каждого свой формат раскладки. Агент, расставляющий абсолютные x/y/w/h, регулярно порождает наложения и дыры. Спек описывает раскладку как список строк, внутри каждой — виджеты с долей ширины из 12; адаптер разворачивает это в родную сетку таргета.

3. Виджет объявляет колонки, которые ожидает получить. Поле declared_columns ловит класс поломок, который иначе проходит незамеченным: запрос по-прежнему выполняется без ошибки, но возвращает другой набор колонок, и график молча пустеет. Валидатор сверяет объявленное с фактическим.

4. Параметры типизированы и подставляются сервером. Агент никогда не конкатенирует значения в SQL — он ссылается на параметр через :name, а сервер рендерит его сам. Это одновременно защита от инъекции и условие портируемости: один и тот же спек превращается в переменную Grafana, в фильтр Superset или в плейсхолдер собственного рендерера.

Скелет

Полный пример: два stat-виджета и график на метриках, таблица на сыром SQL.

{
  "spec_version": "1",
  "uid": "revenue-overview",            // стабильный ключ идемпотентного push
  "title": "Обзор выручки",
  "description": "Динамика и разрез по странам",

  "params": [
    { "name": "period", "type": "time_range", "default": "last_30d" },
    { "name": "country", "type": "enum", "multi": true, "default": [],
      "options": { "from_dimension": { "table": "orders", "column": "country" } } }
  ],

  "rows": [
    { "widgets": [

      { "id": "total_revenue", "width": 3, "viz": "stat", "title": "Выручка",
        "query": {
          "kind": "metric",
          "metric": "revenue",               // → sem_metrics.name
          "time": { "param": "period" },
          "filters": [ { "dimension": "country", "op": "in", "param": "country" } ]
        },
        "encoding": { "value": "revenue", "compare_to": "previous_period" },
        "format": { "unit": "RUB", "decimals": 0 } },

      { "id": "orders_count", "width": 3, "viz": "stat", "title": "Заказы",
        "query": { "kind": "metric", "metric": "orders", "time": { "param": "period" } },
        "encoding": { "value": "orders" } },

      { "id": "revenue_trend", "width": 6, "viz": "line", "title": "Динамика",
        "query": {
          "kind": "metric", "metric": "revenue",
          "grain": "day",                     // разбивка по времени
          "dimensions": ["country"],
          "time": { "param": "period" }
        },
        "encoding": { "x": "ts", "y": ["revenue"], "series": "country" } }
    ]},

    { "widgets": [
      { "id": "top_customers", "width": 12, "viz": "table", "title": "Топ клиентов",
        "query": {
          "kind": "sql",
          "sql": "SELECT customer_id, sum(amount) AS revenue, count() AS orders
                   FROM orders
                   WHERE {{ time_filter(created_at, :period) }}
                     AND {{ filter(country, :country) }}
                   GROUP BY customer_id
                   ORDER BY revenue DESC
                   LIMIT 100",
          "declared_columns": [
            { "name": "customer_id", "type": "UInt64" },
            { "name": "revenue",     "type": "Float64" },
            { "name": "orders",      "type": "UInt64" }
          ]
        },
        "encoding": { "columns": ["customer_id", "revenue", "orders"] } }
    ]}
  ],

  "meta": {
    "origin": "agent",                      // agent | human
    "validation_status": "ok",             // ok | broken | unknown
    "last_validated_at": "2026-08-28T09:14:00Z"
  }
}

Почему вид запроса решает судьбу дашборда

Это главное практическое следствие формата — и причина, по которой агента стоит подталкивать к метрикам.

Практический вывод для промпта агента: сначала search_metrics, и только если подходящей метрики нет — сырой SQL плюс предложение завести метрику через suggest_semantic_update. Так семантический слой растёт естественно, а доля хрупких виджетов падает со временем.

Разбор полей

Параметры

ТипЗначениеВо что превращается

В сыром SQL параметры доступны только через два макроса и ссылку :name:

{{ time_filter(created_at, :period) }}
  → created_at >= toDateTime('...') AND created_at < toDateTime('...')

{{ filter(country, :country) }}
  → country IN ('RU','KZ')     — когда параметр заполнен
  → 1                          — когда пуст

Раскрытие пустого мультиселекта в 1 — мелочь, которая отделяет работающий спек от неработающего: иначе снятый фильтр ломает запрос синтаксически.

Отклонение от реализации. Макросы time_filter и filter в спеке описаны, но пока не разворачиваются сервером: параметры работают на уровне метрик (date_from / date_to в sem_compile_metric) и переменных Grafana. Для виджетов на сыром SQL параметризация — направление развития; сейчас такой SQL пишется с явными условиями.

Типы визуализации и энкодинг

Контракт валидатора

Что именно проверяет фоновый прогон по каждому виджету — и какой статус кладёт в widget_validation.

  1. Запрос компилируется. EXPLAIN с параметрами в значениях по умолчанию — без чтения данных.
  2. Фактические колонки покрывают объявленные. declared_columns сверяются с тем, что реально вернул бы запрос.
  3. Энкодинг ссылается на существующие колонки. Все имена из encoding есть в declared_columns.
  4. Метрика жива. Для kind: "metric" — запись в sem_metrics существует и её статус не orphaned.
  5. Измерения и фильтры существуют. Колонки из dimensions и filters есть в актуальной схеме.
  6. Параметры объявлены. Каждый :name в SQL присутствует в params.

Статусы виджета: ok broken — запрос не компилируется drifted — компилируется, но набор колонок разошёлся с объявленным stale_metric — метрика не найдена или помечена stale. Дашборд получает худший статус среди своих виджетов, а dash_list_broken отдаёт виджет и текст ошибки.

Проверки 1–4 и 6 реализованы в validation.py. Проверка 5 (существование колонок из dimensions и filters) выполняется косвенно: скомпилированный SQL метрики не пройдёт валидацию, если колонки нет.

Уровень поддержки. Помимо описанного здесь, у дашборда есть поле maintenance с тремя значениями: maintained валидируется и попадает в очередь починки, unmaintained хранится без проверок, archived скрыт из выдачи. По умолчанию поддержка выключена — стоимость фонового прогона растёт с числом дашбордов, а разовых отчётов у агента всегда больше, чем постоянных.

Хранение

create table dashboards (
  uid                text primary key,
  title              text not null,
  spec               jsonb not null,
  spec_version       text not null,
  origin             text not null,          -- agent | human
  validation_status  text not null default 'unknown',
  last_validated_at  timestamptz,
  created_at         timestamptz not null default now(),
  updated_at         timestamptz not null default now()
);

create table dashboard_versions (
  uid        text not null references dashboards(uid) on delete cascade,
  version    int  not null,
  spec       jsonb not null,
  author     text,
  note       text,                       -- «починка после переименования revenue»
  created_at timestamptz not null default now(),
  primary key (uid, version)
);

create table widget_validation (
  uid        text not null,
  widget_id  text not null,
  status     text not null,               -- ok | broken | drifted | stale_metric
  error      text,
  checked_at timestamptz not null default now(),
  primary key (uid, widget_id)
);

create index on dashboards using gin (spec jsonb_path_ops);

GIN-индекс окупается одним запросом — анализом влияния перед правкой метрики:

-- какие дашборды сломает изменение определения revenue
select uid, title from dashboards
where spec @? '$.rows[*].widgets[*].query ? (@.kind == "metric" && @.metric == "revenue")';

Как спек ложится в Grafana

Адаптер компилирует спек целиком в один дашборд-JSON и заливает его POST /api/dashboards/db. Метрики разворачиваются в SQL на стороне сервера — в Grafana понятия метрики нет.

Поле спекаВ Grafana
uiddashboard.uid — тот же uid перезаписывает, отсюда идемпотентность
params[time_range]time.from / time.to плюс пикер периода
params[enum]templating.list[] — переменная с запросом за значениями
rows[].widgets[].widthgridPos: доля из 12 умножается на 2 — сетка Grafana 24-колоночная
viztimeseries, barchart, stat, table, piechart, heatmap, text
querytargets[0].rawSql; макросы становятся $__timeFilter() и $var
encodingfieldConfig и transformations — какие поля куда отображаются

Обратный разбор не нужен: валидатор работает по спеку в Postgres, а не по тому, что лежит в Grafana. Именно поэтому push односторонний.

Что оставлено за рамками версии 1

  • Кросс-фильтрация — клик по одному виджету фильтрует остальные. Портируется плохо, стоит дорого; при необходимости лучше решать на собственном рендерере.
  • Drill-down в детализирующий дашборд. Отложить до момента, когда появится реальный запрос от пользователей.
  • Алерты — у Grafana своя модель, дублировать её в спеке смысла нет; проще завести их вручную поверх сгенерированного дашборда.
  • Права доступа — остаются на стороне таргета и вашей аутентификации, в спек не проникают.
